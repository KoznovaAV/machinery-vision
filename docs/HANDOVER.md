# Передача Machinery Vision и сопровождение модели

Актуальная рабочая копия: `D:/machinery-vision/project`. Этот документ описывает локальный прототип и рекомендуемый порядок поддержки. Интеграция в мобильное приложение и автоматическое переобучение здесь не реализованы.

## Зафиксированный локальный выпуск

Текущий выпуск — `maintenance_round6`, 16 ноября 2026 года. Его состав указан в `artifacts/mvp/current_release.json` и `artifacts/mvp/maintenance_round6_release.json`. Проверка: `python -B -m scripts.check_mvp_release`. Веса семейств и состояния сохранены; изменения касаются проверки областей и отказов при неопределённых границах. Это экспериментальная версия для проверки человеком. Визуальная разметка новых данных выполнена ассистентом; её нельзя считать экспертной приёмкой.

Рабочие исходники выпуска дополнительно сохранены в `output/maintenance_round6/release_source/`, версии библиотек опубликованы в `reports/maintenance_round6/runtime_versions.json`. Копия исходников также фиксируется Git-коммитом выпуска. Предыдущие веса проверки областей находятся в `output/maintenance_round6/baseline/`. Выбирать файлы по самому новому времени изменения нельзя: нужно следовать манифесту.

Для полного отката будущих изменений нужны вместе код, веса, справочник и пороги проверенного выпуска. Папка baseline содержит прежние веса; она не является полным снимком всех исходников прежней версии. Исходный код фиксируется Git-коммитом этого выпуска; отдельную копию данных/артефактов нужно передать средствами организации. Команды нового клонирования и запуска — в README.

## Что передать следующему ответственному

- Локальную рабочую копию со всеми исходниками и `requirements-hierarchy.txt`, а не только ссылку на GitHub. Исходники и компактный комплект MVP публикуются в этом репозитории; фотографии и большие базовые веса в Git не включены.
- `artifacts/mvp/` целиком: взаимосвязанные головы, эталоны, калибровка и манифесты с SHA. Нельзя отдельно заменить файл весов, забыв про справочник классов и пороги.
- `configs/machinery_taxonomy.json`: тип, семейство, серия, группа моделей и точная модель имеют разный смысл.
- Файлы энкодеров/детектора из `weights/`, ConvNeXt из `D:/machinery-vision/envs/torch-cache/hub/checkpoints/` и рабочее Python-окружение либо воспроизводимую установку зависимостей. В новом клоне большие базовые веса нужно загрузить командой `python -B -m scripts.setup_hierarchy_weights` с заданным `TORCH_HOME`; см. README. Фото и рабочие данные для повторного обучения передаются отдельно.
- Манифесты и изображения датасетов, на которые они ссылаются, включая `data/` и обучающие/контрольные папки `output/`. Нельзя передать только JSON без фотографий. Объёмные данные и права на их распространение нужно проверить перед передачей за пределы организации.
- Последний отчёт и список ограничений из [CURRENT.md](CURRENT.md). Старые отчёты сохраняются как история экспериментов, а не описание текущего выпуска.

До передачи нужны два назначенных владельца функций: человек, который может проверить модель техники и состояние по фото, и инженер, который запускает проверки и выпускает версии. Это могут быть один или два сотрудника. Если владельца пока нет, оставить проверенную версию замороженной; обучение и замену весов не запускать автоматически.

```powershell
Set-Location 'D:/machinery-vision/project'

$env:PYTHONUTF8 = '1'
```

Если порт уже занят, использовать работающий интерфейс <http://127.0.0.1:7864/>. Не запускать второй экземпляр на том же порту и не завершать произвольные процессы Python.

Не запускать интеграцию с неполным или несовпадающим комплектом весов. Проверка целостности не заменяет проверку качества и полного распознавания.

Минимальный приёмочный прогон: одна чистая и одна явно грязная машина; снег; ночь; три машины, включая частично обрезанную; трактор с прицепом/цистерной; настоящий комбайн, частично скрытый другой машиной; неподдерживаемая модель с читаемой маркировкой. Проверять также корректный отказ, а не требовать точный ответ на каждом фото.

## Что подключать к мобильному приложению

Текущий локальный веб-интерфейс — средство проверки человеком: `scripts/serve_hierarchy_review.py`, `/predict` возвращает HTML. Он привязан к локальному компьютеру и не является готовым публичным мобильным API.

В проекте также есть старый API v3 с четырьмя семействами. Он отличается от текущего иерархического MVP. Нельзя ожидать от старого API всех возможностей нового конвейера.

Для первого внедрения рекомендую серверное распознавание с отдельным JSON-адаптером к `scripts.predict_machinery_hierarchy.run`: приложение передаёт фото, сервер возвращает список объектов, тип, семейство, кандидатов, неопределённость и видимое состояние. Потребуются версия модели в ответе, ограничения нагрузки, обработка ошибок и защита доступа. Это будущая работа, в текущем прототипе она не выполнена.

Перенос полного конвейера на телефон — отдельный эксперимент: детектор, два энкодера и OCR нужно проверить по памяти, задержке и качеству после оптимизации. Само преобразование формата весов не гарантирует прежнюю точность.

## Может ли модель улучшаться сама

Текущая модель использует сохранённые веса. Новое распознавание не изменяет эти веса. Самообучение появится только при специально реализованном контуре.

Рекомендуемый для этого проекта контур:

1. С согласия пользователя сохранить фото, результат, версию модели и исправление пользователя в очередь. До проверки это кандидаты для разметки, не обучающая истина.
2. Ответственный проверяет модель/семейство, состояние, число машин и области объектов. «Семейство известно, точная модель неясна» — допустимая разметка. Для дождя нужны видимые признаки дождя; мокрая дорога сама по себе не доказывает мокрую машину.
3. Дедупликация по хешам и похожести, группировка одной машины, объявления или серии кадров. Вся группа остаётся в одном разбиении. Прежний контроль не подмешивать в обучение.
4. Отдельная задача обучения создаёт новую версию-кандидата. Работающее приложение продолжает использовать прежнюю версию.
5. Автоматические проверки оценивают каждый прежний класс и погодный срез, ошибки уверенных ответов, пропуски машин и ложные прицепы. Отказы учитывать отдельно от ошибок. Тестировать также время и память на целевом устройстве/сервере.
6. Назначенный инженер просматривает отчёт и утверждает выпуск. Сначала ограниченное внедрение, затем расширение при нормальных результатах. Сохраняются прежний комплект и возможность отката.

Сбор очереди, дедупликацию, обучение кандидатов и сравнение можно автоматизировать. **Самостоятельную замену рабочей модели по непроверенным ответам пользователей или собственным прогнозам сейчас не рекомендую.** В экспериментах этого проекта добавление данных уже неоднократно снижало число верных ответов на прежних классах.

Если назначить человека невозможно, разумнее стабильная версия плюс очередь обратной связи без автоматической публикации. Работа модели может продолжаться без постоянного переобучения; её качество при изменении техники и условий всё равно потребует периодической проверки.

## Важное ограничение старого контура обратной связи

`scripts/ingest_feedback.py` относится к старому API v3. В режиме с разрешённым предсказанием состояния он может подставить прогноз модели вместо отсутствующей пользовательской метки. Это создаёт риск обучения на собственных ошибках. Он не запускается автоматически текущим веб-интерфейсом.

Для ручного разбора старого контура использовать сначала сухой прогон с обязательной меткой:

```powershell
& $python -B -m scripts.ingest_feedback --dry-run --require-user-state --verbose
```

Флаг требует пользовательскую метку, но сам по себе не подтверждает её проверку экспертом. Реальное применение допустимо только после проверки очереди и защиты контрольных групп. Этот скрипт не следует подключать к расписанию автоматического обучения текущей иерархической модели без переделки формата и правил допуска данных.

## Минимальный журнал выпуска

Для каждого выпуска хранить: идентификатор версии, SHA всех артефактов, справочник классов, версии кода/зависимостей, манифест данных с группами, результаты сравнения по классам и условиям, перечень обученных обратных примеров, известные ошибки, имя утвердившего выпуск и комплект отката. Обученные обратные примеры не выдавать за независимый тест.

Текущий контроль многократно использовался для диагностики. Для итоговой оценки следующей версии нужен новый набор от других владельцев и съёмок. Новые состояния нельзя считать надёжно поддержанными, пока нет достаточного отдельного контроля положительных и отрицательных примеров.

Показатели эксплуатации: ошибки сервиса, задержка, частота отказов и распределение входных фото. Реальную точность измерять по проверенной разметке: высокая уверенность модели или согласие с собственным прошлым ответом не являются измерением точности.

Основание для рекомендуемого контура: [Google Cloud — MLOps: Continuous delivery and automation pipelines in machine learning](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning). Конкретные роли, ручное утверждение и запрет автоматической замены — рекомендации для нынешней зрелости нашего проекта, а не уже реализованные функции приложения.
